# Airflow on Hopsworks

## Concept

Airflow on Hopsworks orchestrates **Hopsworks jobs, and nothing else**. A task
launches a job that already exists in a project and waits for it; the work itself
runs in the Hopsworks job, not in the Airflow worker. Airflow is the scheduler
and the dependency graph, not an execution engine.

This is the shape of every DAG: define the jobs first (Spark, PySpark, Python,
Ray, or a feature pipeline), then write a DAG that launches them in order.

## Key facts / rules

- **DAG files must live in the project's `Airflow` dataset.** The scheduler only
  picks up files there. In the project that is the `Airflow` dataset, on disk
  `/Projects/<project>/Airflow/`. A DAG anywhere else, including a Jupyter
  working directory or `Resources`, is never scheduled.
- **Only Hopsworks operators are supported.** There is no BashOperator,
  PythonOperator, KubernetesPodOperator or Docker task. Anything you want to run
  must first be a Hopsworks job.
- The supported operators and sensors are:

  | Symbol | Purpose |
  | --- | --- |
  | `HopsworksLaunchOperator` | Start a named job in a project |
  | `HopsworksJobSuccessSensor` | Wait for a launched job to succeed |
  | `HopsworksHdfsSensor` | Wait for a path to appear in the project's file system |

- **A DAG belongs to one project.** The `project_id` on each task is what scopes
  it; moving the file does not move the DAG between projects.
- **Do not put an API key in the DAG file.** Each DAG gets a project-scoped
  Hopsworks API key stored as an Airflow Variable and read by the hook at task
  runtime, so the file carries no secret and is safe to inspect and commit.
- A launch and its sensor are two tasks: `HopsworksLaunchOperator` returns once
  the job is *started*, and `HopsworksJobSuccessSensor` is what waits for it to
  finish. Chaining launches without the sensor gives you a race, not a pipeline.
- Hopsworks can generate the DAG for you from the UI; the generated file carries
  a "Generated by Hopsworks. Do not edit by hand." header, and re-composing
  overwrites it. Hand-written DAGs go in the same dataset under a different name.

## Commands / API

```python
from datetime import datetime
from airflow import DAG
from hopsworks.airflow.operators import HopsworksLaunchOperator
from hopsworks.airflow.sensors import HopsworksJobSuccessSensor

with DAG(
    dag_id="feature_pipeline_daily",
    start_date=datetime(2025, 1, 1),
    schedule="0 2 * * *",
    catchup=False,
) as dag:
    ingest = HopsworksLaunchOperator(
        task_id="ingest",
        project_id=119,
        job_name="transactions_ingest",
    )
    ingest_done = HopsworksJobSuccessSensor(
        task_id="ingest_done",
        project_id=119,
        job_name="transactions_ingest",
        launch_task_id="ingest",
    )
    train = HopsworksLaunchOperator(
        task_id="train",
        project_id=119,
        job_name="fraud_model_training",
    )
    ingest >> ingest_done >> train
```

Upload it into the `Airflow` dataset so the scheduler sees it:

```bash
hops dataset upload feature_pipeline_daily.py Airflow
```

On Airflow 3 the operators come from the provider package
`apache-airflow-providers-hopsworks` rather than a plugin import.
